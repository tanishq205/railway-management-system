## 2. Relational Normalization Analysis (1NF, 2NF, 3NF & BCNF)

### First Normal Form (1NF)
- **Criterion**: All attributes are atomic (no repeating groups, CSV lists, or array values).
- **Compliance**: Passenger lists are decomposed into `Ticket_Detail` rather than stored as delimited strings in `Ticket_Header`. Each column contains atomic domain values.

### Second Normal Form (2NF)
- **Criterion**: Meets 1NF, and no non-prime attribute is partially dependent on any candidate key.
- **Compliance**: Every table with surrogate identity keys (`GENERATED BY DEFAULT AS IDENTITY` or single-attribute `PNR`) is inherently in 2NF. In tables with compound candidate keys (e.g., `(Train_ID, Stop_Sequence)` in `Route_Schedule`), all timing attributes (`Arrival_Time`, `Departure_Time`) depend on the specific sequence of the train stop, not on `Train_ID` alone.

### Third Normal Form (3NF)
- **Criterion**: Meets 2NF, and no non-prime attribute is transitively dependent on the primary key ($X \to Y$ and $Y \to Z$).
- **Compliance**:
  - `Coach` does not duplicate coach capacity; capacity is derived dynamically via `COUNT(Seat_ID)`.
  - `Ticket_Header` stores references to `From_Station_ID` and `To_Station_ID`, but does not store redundant station names or state codes (eliminating transitive dependency).
  - Physical maintenance condition (`Seat.Physical_Condition`) is decoupled from runtime availability (`Seat_Allocation.Booking_Status`).

### Boyce-Codd Normal Form (BCNF) Discussion
- In `Route_Schedule`, we have two candidate keys: `Schedule_ID` and `(Train_ID, Stop_Sequence)`, plus the constraint `(Train_ID, Station_ID)`. Both candidate keys are functional determinants for all other attributes. 
- The schema is maintained in strict 3NF. While most relations satisfy BCNF, full BCNF across all composite operational dependencies is evaluated pragmatically to maintain database performance and enforce foreign key referential actions (`ON DELETE CASCADE`) natively.

## 3. PostgreSQL PL/pgSQL Triggers & Views

### Triggers (Functions returning TRIGGER)
1. **`trg_seat_allocation_audit`**: Fires `AFTER UPDATE ON Seat_Allocation`. If `Booking_Status` changes, executes `fn_seat_allocation_audit()` to log `'SEAT_STATUS_<OLD>_TO_<NEW>'` in `Audit_Log`.
2. **`trg_payment_audit`**: Fires `AFTER INSERT ON Payment`. Executes `fn_payment_audit()` to log `'PAYMENT_<STATUS>_<PNR>'` in `Audit_Log`.
3. **`trg_sync_seat_condition`**: Fires `AFTER UPDATE OF Physical_Condition ON Seat`. Automatically synchronizes `Seat_Allocation` (`AVAILABLE` &harr; `BLOCKED`) and logs maintenance events in `Audit_Log`.
4. **`trg_prevent_repair_seat_booking`**: Fires `BEFORE INSERT OR UPDATE OF Booking_Status ON Seat_Allocation`. Raises an exception if a seat marked `UNDER_REPAIR` is booked.
5. **`trg_train_run_status_audit`**: Fires `AFTER UPDATE OF Run_Status ON Train_Run`. Logs `'RUN_STATUS_<OLD>_TO_<NEW>'` into `Audit_Log`.
6. **`trg_validate_train_stations`**: Fires `BEFORE INSERT OR UPDATE OF Source_ID, Destination_ID ON Train`. Prevents creating a train with identical source and destination stations.

### Database Views
1. `vw_booking_details`: Consolidates multi-table joins for fast PNR resolution and passenger history.
2. `vw_train_occupancy`: Real-time calculation of capacity, booked, available, blocked seats, and occupancy percentages per train run.
3. `vw_revenue_summary`: Aggregates gross, refunded, and net revenue by train service and date.
4. `vw_route_timetable`: Ordered train route stops with station codes, cities, arrival, and departure times.
5. `vw_audit_trail`: Joins `Audit_Log` with `User_Account` for enriched security and trigger event auditing.

## 4. ACID Transactions & Concurrency Control (PostgreSQL MVCC)

Railway ticket booking is a classic concurrent reservation scenario susceptible to **Race Conditions** and **Double-Booking Overwrites**.

### Concurrency Mechanism: Row-Level Locking with PostgreSQL
When concurrent passengers attempt to book the last available seat on a train run:
1. `BEGIN;` begins an atomic transaction on a dedicated pooled client.
2. `SELECT Allocation_ID, Seat_ID, Booking_Status FROM Seat_Allocation WHERE Run_ID = $1 AND Booking_Status = 'AVAILABLE' LIMIT $2 FOR UPDATE;`
   - The `FOR UPDATE` clause places an exclusive row-level lock on the matching `Seat_Allocation` rows.
   - Any concurrent transaction attempting to read or modify those exact rows will be queued until the first transaction commits or rolls back.
3. The backend rechecks that the returned row count satisfies the requested passenger count.
4. If available:
   - Sets `Booking_Status = 'BOOKED'`
   - Inserts `Ticket_Header` and `Ticket_Detail`
   - Inserts simulated `Payment` record
   - Executes `COMMIT;` (locks released, changes persisted)
5. If payment simulation fails:
   - Executes `ROLLBACK;` (all changes reverted, seat locks released immediately).

## 5. Viva Q&A Quick Reference

**Q: Why use Supabase PostgreSQL instead of MySQL or SQLite?**  
**A:** Supabase PostgreSQL is an enterprise cloud RDBMS providing strict ACID compliance, Multi-Version Concurrency Control (MVCC), PL/pgSQL stored functions, native identity columns (`GENERATED BY DEFAULT AS IDENTITY`), and rock-solid relational integrity.

**Q: Why separate Train and Train_Run?**  
**A:** `Train` represents physical rolling stock metadata (e.g., Train 12951 Rajdhani Express), whereas `Train_Run` represents the operational service instance on a specific date (e.g., Rajdhani on October 30, 2026). This cleanly models recurring daily/weekly schedules.

**Q: Why separate Seat and Seat_Allocation?**  
**A:** `Seat` represents physical hardware in a coach (e.g., Coach A1, Seat 12). Its condition (`OPERATIONAL` or `UNDER_REPAIR`) is physical. `Seat_Allocation` tracks whether that physical seat is `AVAILABLE`, `BOOKED`, or `BLOCKED` for a particular date's `Train_Run`.

**Q: How is SQL Injection prevented?**  
**A:** All database queries in the backend use prepared statements with parameterized placeholders (`$1, $2, ...`) provided by the `pg` driver. User input is never concatenated into SQL query strings.
